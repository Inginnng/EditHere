# 反馈交接与跟进任务的生命周期

默认采用手动继续：批注页打开后结束本轮，用户点击“反馈”，回到对话说“继续”时读取原会话。无需创建宿主定时任务。

EditHere CLI 没有宿主唤醒回调，也没有页面关闭或在线状态回执。网页顶部“取消”会取消服务端会话；关闭标签或右侧面板不会自动取消，poll 仍可能返回 pending。不能仅靠技能文字补出程序事件。

## 保存原会话

在当前任务目录写入 `.edithere/sessions/<sessionId>.json`，至少包含实际的 `sessionId/url/image/imageSource/node/cli/output/expiresAt/taskScope`，以及：

```json
{
  "followUpMode": "manual",
  "followUp": null,
  "handling": {"state": "pending", "sha256": null},
  "consecutiveErrors": 0
}
```

沿用 start 回执的 ID、输出和 Unix 毫秒到期时间。不要存示例路径，打印 URL 访问令牌，或拼接记录中的路径后求值。

手动“继续”时对原 ID poll 一次；completed 按下文核验与防重复处理，pending 则告知尚未提交并结束，不改为循环等待或自行注册任务。已停止的记录只有用户明确恢复才继续读取；恢复仍默认手动，不重建已删除的任务。

## 用户明确选择定时跟进时

定时任务在当前对话中定期唤醒，不是隐藏的文件监听。“pending 不回复”不能保证宿主不显示“由已安排任务发送”。启用时准确说明调度留痕和延迟，不能称为完全无痕。

1. 仅在本次会话已获得定时跟进授权时注册。一次历史选择不代表所有后续会话都要调度；明确覆盖本次的授权不用重复确认。
2. 检查可用工具能否可靠观察**本次**批注页关闭。可用浏览器工具取得完整相关浏览器标签清单时，保存已确认载入的 URL、浏览器和 tabId，用于后续精确匹配。面板隐藏、浏览器失焦、切换标签或工具读取失败不代表关闭。仅有当前 URL 的环境快照不能证明其他标签不存在。
3. 没有可靠关闭检测时，默认手动继续。用户明确要求离开页面也继续定时跟进时可注册，但应说明此模式依靠用户取消、提交或到期停止，不能承诺关闭自动停止。
4. 发现已有本次 session 的任务时先查看并复用。已被替换的旧会话应清理原调度，保留旧图片和批注，不同时留下两个有效跟进。
5. 使用宿主 `automation_update`，`kind:"heartbeat"`、`destination:"thread"`，附着当前对话；不要另建 cron 或新对话。默认每 2 分钟查询一次。遵守工具当前参数说明。
6. 保存真实自动化 ID 与可供更新的完整配置到 `followUp`，设置 `followUpMode:"heartbeat"`。成功才能承诺自动跟进。创建成功而记录失败时立即删除刚创建的任务，保持手动继续。

通知设置使用工具字段，保留用户偏好；不要把通知设置写进调度提示词。以下是每次唤醒的工作内容示例，替换为实际记录路径：

```text
跟进 EditHere 批注。读取已安装的 edithere-web 技能和会话记录：<本次记录的绝对路径>。
先检查 followUp 和 handling：已删除、已停止、handled、processing、needs_review 时不自动恢复或重复实施；清理仍存在的原调度，结束。
用户已明确关闭或取消，或可靠完整标签清单确认本次已载入的批注页不再存在时，清理原任务并记录 stopped，不重开页面或另建会话。
否则每次唤醒最多对原 sessionId poll 一次，不 wait、sleep 或启动轮询进程。
pending 且未到期时保留待提交状态，结束，不输出例行进度或催促。
completed 时核验本次反馈与 SHA，先登记 processing 并清理原调度，再继续 taskScope 内已授权的工作，最后报告结果。
cancelled、expired 或到期仍未完成时清理原调度，记录原因，只报告一次。到期仍先查询一次，以免遗漏已提交反馈。
查询失败保留诊断和连续失败次数，未满 3 次时留待下次调度；连续 3 次时清理调度并报告阻塞。
```

## 每次唤醒先检查是否已停止

读取本记录与当前用户消息。`followUp.status` 为 DELETED 或 PAUSED、`followUpMode` 为 manual，或 `handling.state` 为 stopped/handled/processing/needs_review 时，不 poll、不自动实施、不重新注册；若宿主仍有残留的原任务，清理它。已经排队的一次唤醒也遵守此规则。

用户说已关闭、不再等待或取消，直接按下文清理关联调度，不要求他重新打开页面按取消。可靠工具确认页已关闭时同样处理；没有关闭证据时不虚构检测结果。保留原图和会话记录，关闭不代表反馈已提交。

仍在跟进时，用已保存的 Node.js 和 CLI 对原 sessionId poll 一次，匹配本次图片与 output。正常查询清零连续错误次数。

| 查询结果 | 处理 |
| --- | --- |
| pending，未到期 | 保留待提交状态，结束，不发例行进度。 |
| completed | 核验、防重复、清理任务，再处理授权范围。 |
| cancelled / expired | 清理任务，记录原因，只报告一次。 |
| 已到期 | 仍先查询一次；若未完成或查询失败，清理任务并记录诊断。 |
| 查询或解析失败 | 保存诊断与连续失败次数，满 3 次清理任务并报告一次，不循环重试。 |

## 清理宿主任务

临时批注跟进结束时，优先通过宿主工具删除原自动化，使任务不继续触发，也不在任务列表留下暂停项。用户要求暂时暂停、之后恢复时才采用 PAUSED；暂停和删除的效果须准确说明。

有有效 ID 时先查看原配置，再使用工具支持的删除操作；若工具仅支持暂停，保留其余字段更新为 PAUSED，并说明仍保留暂停条目。不要直接修改宿主自动化 TOML。工具回执确认成功后，将状态及终止时间、原因、操作回执保存到 followUp。已删除或不存在的任务无需重新创建。

用户关闭、取消、会话被替换或错误终止时，待提交的 handling.state 记为 stopped（仅表示本地跟进停止，不伪称服务端已取消）。已有 handled/processing/needs_review 及 SHA、completedAt 等处理历史必须保留，避免后来手动继续时重做；停止原因写在 followUp。用户明确要求取消服务端会话时可执行原 ID 的 cancel；清理宿主任务不依赖 cancel 成功。

无法删除或暂停时记录实际错误及自动化 ID，报告一次具体限制，不能声称已停止。不得靠提示词“停止”或空回复代替真实清理。

## completed 的防重复处理

1. 核验回执 sessionId/output 与本记录一致，反馈能解析。含 sha256 时核对本次输出文件 SHA-256；空批注有效，不打印图片 base64。
2. 同一 SHA 已 handled 时不重做。processing/needs_review 表示可能部分处理，先核实结果，不自动重放。
3. 在任何反馈实施前写 handling 为 processing，保存 SHA/completedAt，并清理已注册的任务。清理失败则写 needs_review，停止依赖操作并报告实际错误。
4. 继续 taskScope：仅收集则概括意见；已授权实施则修改并验证。成功写 handled；中途失败保留变更及诊断并写 needs_review。

## 无调度或登记失败

保留原会话，说明“提交后回到对话说‘继续’”。不得创建替代会话、启动后台 CLI 轮询或宣称结束回复后仍会自动跟进。本地定时任务依赖宿主和电脑可运行，不能保证提交后立即处理。
