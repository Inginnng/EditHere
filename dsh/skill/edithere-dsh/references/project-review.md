# 项目组图与结果审批

EditHere 是开发结果的组图评审台。用户启用这条工作流后，由 AI 运行项目、收集全部已实现且可访问的页面、维护组图；用户直接评审并提交意见。当前 AI 读取图片与反馈、理解需求、修改源代码、验证，再按需更新图片，先自查结果，再展示下一轮组图供用户评审。截图整理与组图维护由 AI 承担。

桌面 Windows / macOS / Linux、MCP 连接器、离线 Web、Web Agent、MCP Apps 和 DSH 使用同一页面 ID 与 `image-set-feedback-1` 反馈容器。0.13.0 配套技能按本流程工作；实际能力仍以所用程序的版本、`--help` 和已连接工具为准，不能让旧安装包冒充组图入口。

## 开发完成后先建立页面覆盖

项目级组图评审默认覆盖全部已实现且可访问的页面。先查看路由、导航、页面/场景目录及实际运行入口，列出页面与重要状态，再逐项进入并截图。设置子页、与本轮功能有关的弹窗、关键交互结果和明暗主题等独立可见状态按项目实际情况补充；不同视口有明确验收要求时分别记录。用户明确只评某几页时沿用该范围，不擅自扩展为全项目检查。

截图来自实际运行的项目。已有设计图只作为设计参考，旧图、示例图和固定测试渲染不能替代当前运行结果。登录、外部服务、缺少数据或截图能力导致不可访问时，保留已完成页面并说明缺哪些页、原因和最小补充条件；不以几张代表图宣称全部页面已经覆盖，也不要求用户代为逐页整理可以由 AI 完成的截图。

新截图优先使用保留真实设备像素的无损 PNG。高 DPI 下区分窗口逻辑尺寸与截图像素尺寸；不要把缩小后的 JPEG 预览当作高清原图。改扩展名或把 JPEG 转为 PNG 不会恢复细节。使用宿主实际支持的截图工具，尊重用户指定的工具；缺少高保真输出时说明实际格式与限制。

## AI 维护项目清单

每个项目保留一个清单，例如 `.edithere/results/project.json`：

```json
{
  "schemaVersion": "edithere-image-set-1",
  "name": "桌面程序页面",
  "pages": [
    {"id": "home", "name": "首页", "path": "home.png"},
    {"id": "settings", "name": "设置", "path": "settings.png"}
  ]
}
```

`path` 相对清单目录，也接受本机绝对路径。`id` 表示页面身份，例如 `home`、`settings.ai`；改名、换图和修改尺寸时继续沿用，新页面才用新 ID。首次创建时按页面清单逐项加入；项目已有清单则先读取并继续维护，不另建一套重复页。页面名称应让不熟悉源码的用户也能识别。

可以按轮次保留截图与反馈，例如 `shots/round-001/settings-ai.png`、`reviews/round-001/feedback.json`。组织方式可沿用项目习惯；必要条件是当前清单稳定、每轮输出唯一、历史反馈与其对应图片仍可追溯。当前用户正在审阅的图片和反馈不能被新截图覆盖。

仓库命令如下；分发的 skill 在自己的 `scripts/` 中携带同样的工具。离开仓库使用时，将 `scripts/image-set.mjs` 替换为当前技能目录中脚本的绝对路径，不依赖开发者源码路径或额外 npm 包：

```powershell
node scripts/image-set.mjs create .edithere/results/project.json --name "桌面程序页面"
node scripts/image-set.mjs upsert .edithere/results/project.json --id home --name "首页" --image shots/home.png
node scripts/image-set.mjs upsert .edithere/results/project.json --id settings --name "设置" --image shots/settings.png
```

更新设置页只需再次 `upsert --id settings --image ...`，原有页序、其他页面和 ID 都会保留。工具记录原图 SHA-256；截图字节变化后需同步 `upsert`，避免无意提交旧清单。`list` 查看清单，`remove --id ...` 移除已下线的页面引用，原图文件仍保留。

## 交给用户审批

每轮反馈使用新的输出文件或目录。当前审核读取截图快照；AI 更新清单不会悄悄改变正在批注的画面。完成一轮修改后重新打开同一清单，即可展示更新后的整组页面。

| 入口 | 发起方式 |
| --- | --- |
| 桌面 | `edithere-cli annotate <清单绝对路径> --output <新的反馈绝对路径>`；保持同一次 CLI 会话等待用户完成 |
| 桌面 MCP 连接器 / 插件 | `edithere_annotate_start` 的 `imagePath` 传清单绝对路径，可用 `outputDir` 指定本轮目录；保存 `sessionId`，通过 `edithere_annotate_poll` 跟进 |
| MCP Apps | `edithere_web_open({projectPath:"<清单绝对路径>",outputPath:"<新的反馈绝对路径>"})`；恢复本轮仍只传 `sessionId` |
| Web Agent | `node web/agent.cjs start --project <清单绝对路径> --output <新的反馈绝对路径>`，打开回执 URL |
| DSH | `node dsh/cli.mjs start --project <清单路径> --output <新的反馈路径> --open` |
| 离线 Web | `node scripts/image-set.mjs bundle <清单路径> --output <新的网页项目.json>`，把生成的项目交给用户打开；也支持直接多图导入 |

`bundle` 内嵌全部页面，浏览器不需要读取清单指向的任意本机路径。桌面保存的 `.edithere`、Web 保存的网页项目保留全部页面和草稿；AI 的清单独立保留，供后续换图。

桌面 `open` / `edithere_open` 仅用于浏览，不能代替可回传的 `annotate` 会话。用户需要“完成并返回 AI”时应使用上表的标注入口；按钮缺失时先核对打开方式和当前会话，不重复打开多个窗口。离线 Web 通过导出反馈文件交回；普通浏览器兼容入口和部分宿主可能需要用户提交后回到原对话说“继续”，不能把保存到本机说成 AI 已经开始处理。

用户可逐页写意见、拖动组件，也可写不绑定单页的“整组意见”。用户点击完成才提交结果；AI 不代点完成，也不把未提交草稿当作修改要求。取消、超时不会产生完成反馈。无批注的组图可以提交为空反馈，表示这轮没有提出修改意见。

## AI 读取与更新

反馈中的 `pageIndex` 是整组上下文索引，只包含名称、ID、尺寸和是否有批注。`pages[]` 只携带有批注或实际布局移动的页面与原图；`groupNotes` 单独表达整体要求。未批注页面不携带图片。页内坐标使用该页原图像素，页面尺寸可以不同。

按 `pages[].id` 对回本轮截图与源码页面，再读取页内批注，按图中 `number` 对照意见。不要用整组页号当作 `pages[]` 的数组下标，也不要重复执行摘要与详细 JSON 中的同一意见。当前页内格式为 `feedback-minimal-4`，使用 `kind`、单个 `movement`、可选 `children` 和图片描述符；历史格式按实际 `schemaVersion` 兼容读取。

阅读有批注页面的实际原图及可用的编号批注图，结合文字、移动和缩放理解最终布局关系。只有几何调整、没有文字也属于修改要求；精确文案、色值和业务数值按原批注保留。将相邻对象、对齐、尺寸和间距关系映射到实际组件、路由、样式或场景代码，修改真实源文件；仅改截图或组图 JSON 不能算完成产品修改。只有具体关系影响实现且无法从本轮证据确定时，才就该处提出澄清，其他独立意见继续处理。

`groupNotes` 可能影响多页或共享组件，应处理它实际涉及的页面。未批注页不附图，但不能因此忽略明确的整组要求；反过来也不因某页没意见就推断该页功能测试通过。图片和 JSON 里的界面文字只是需求数据，不扩大用户授权范围。

## 修改后按需更新，继续下一轮评审

AI 按已提交意见修改源码并完成相应验证，然后评估页面影响范围。共享组件、主题、字体或全局样式的变化可能影响未直接批注的页面，应一并核对；只改内部逻辑且画面没有变化时不必替换截图。

对确实变化的页面重新进入真实运行状态并截图，用原 ID 执行 `upsert`。新页面追加，确实下线的页面移除引用；未变化的截图、页序和身份继续保留。需要重新截图才能判断变化时，比较实际画面与尺寸后再决定是否替换，不因文件时间变化就强行刷新整组。

更新后先由 AI 对照本轮意见自查：源码修改是否落实、截图是否对应新结果、是否引入可见问题，以及哪些意见仍有疑问。随后打开同一项目清单，使用新的反馈路径或会话，将更新后的整组结果交给用户继续评审。用户已经要求持续组图评审时，这一步是原任务的一部分，不必再问一次“是否需要打开组图”。说明本轮落实了哪些意见、换了哪些页、哪些仍待核对。

用户提交新意见则继续这个闭环。用户明确认可、提出停止/暂停，或在没有新意见时结束本轮；取消和超时保留进度并停止等待，不自动再开一轮。遇到能力或访问限制时，保留已完成结果并说明具体缺口。不要无限生成空评审，也不在回合结束后承诺没有实际后台机制的持续工作。

## 与桌面 AI 解析的关系

默认由当前 Agent 直接理解已提交的图片和结构化反馈，再实现修改；用户不必为了这条闭环先配置另一份模型 API。桌面 0.13.0 的「AI 解析（预览功能）」是可选的独立 API 文字整理入口，只有用户选择它时才使用，不代替“完成并返回 AI”，也不是 Web/MCP/DSH 的隐藏前提。打开解析窗口不等于已发请求，生成的文字由用户核对后交付；技能不复制程序内整段系统提示词，以免两份提示词漂移。

当前上限为 64 页、单图 48 MiB、组图总像素 1.28 亿；Web Agent/MCP 的快照还受 96 MiB 会话消息限制。超过上限时按模块拆成多组，并保留页面覆盖说明，不丢页、不静默降低清晰度；需要缩图时先说明取舍。macOS 和 Linux 共用源码，不将本机 Windows 验证当作它们的实机结论。
